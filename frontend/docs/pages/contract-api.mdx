# Contract API

Veil has two Soroban contracts:

- **`invisible_wallet`** is the wallet itself. It is a custom account contract: it implements `__check_auth`, so a passkey (WebAuthn, P-256) signature can authorise transactions for it.
- **`factory`** deploys one wallet per passkey, at an address derived from the passkey's public key.

| | Wallet | Factory |
|---|---|---|
| Crate | `invisible-wallet v0.1.0` | `factory v0.1.0` |
| Source | `contracts/invisible_wallet/src/lib.rs` | `contracts/factory/src/lib.rs` |
| Soroban SDK | `soroban-sdk = "22.0.0"` | `soroban-sdk = "22.0.0"` |
| Public functions in source | 29 | 4 |
| Public functions live on mainnet | 24 | 3 |

## Mainnet and source are not the same contract

<Callout type="warning">
  **The deployed wallet and factory are permanent.** Neither contract has an upgrade entrypoint, so the code running on mainnet will never change. A function marked **Source only** below does not exist on any mainnet wallet and **cannot be added to one**: not by an upgrade, not by the owner, not by Veil. Calling it on a mainnet wallet fails because the function does not exist.
</Callout>

The mainnet factory and every wallet it deploys were built from one commit. `contracts/deployments.json` records it:

| | Value |
|---|---|
| Source commit | `ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2` |
| Factory contract | `CCZ3JLRESNLDADGXWNEH4YQ4NXUUAHRJNCWZHYG6QB4KTDYHOH6OQ7BK` |
| Factory WASM SHA-256 | `3a6756d28de795177be28c2359347e57ea4c244cbe609b86facec00ef1abb853` |
| Wallet WASM SHA-256 | `b485f817469402ba4ccc24ea30077308f69589cbe0897db49087b15f58659ea5` |

`scripts/verify-deployed-hashes.mjs` checks these hashes against the ledger. Source on `main` has moved on since that commit. A future factory deployed from newer source would serve the newer wallet, but it would be a new contract at a new address. It would not change the wallets that already exist.

### How each entry is marked

Every function below carries one of two labels:

- **Live on mainnet.** The function is a `pub fn` in the contract both at `ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2` and on `main`. If its signature or behaviour has changed since, the entry shows the mainnet version too.
- **Source only (not deployed).** The function exists on `main` but not at `ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2`. No mainnet wallet or factory has it.

The labels come from comparing the two versions of each file:

```bash
git show ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2:contracts/invisible_wallet/src/lib.rs
git show ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2:contracts/factory/src/lib.rs
```

The source-only functions are `revoke_allowance`, `get_pending_recovery`, `register_session_key_scoped`, `remove_all_key_spend_limits` and `get_key_spend_limit_tokens` on the wallet, and `set_wasm_hash` on the factory.

### Who can authorise a call

Each entry says who must authorise the call:

- **Wallet owner.** The function calls `env.current_contract_address().require_auth()`. The wallet then authorises itself through `__check_auth`, which in practice means a registered passkey signs the transaction. (A session key or an allowance can also satisfy `__check_auth`, but only for the calls its own limits permit. See [`__check_auth`](#__check_auth).)
- **Guardian**, **recovery key** or **factory admin.** The function calls `require_auth()` on that stored address.
- **Anyone.** The function needs no authorisation. Read-only functions are in this group, and so are the two recovery finalisers, which can only take effect once their timelock has passed.

### Errors

Wallet functions fail with a `WalletError` code. The full list of codes, with causes and recovery steps, is on the **[SDK Error Reference](/sdk-errors#contract-error-codes-walleterror)**. This page only names the codes each function can return.

Some failures are host traps, not `WalletError` codes. A failed authorisation, a failed P-256 or ed25519 signature check, and an explicit `panic!` all surface as a host error.

## Wallet contract

### `init`

**Status:** Live on mainnet · **Authorisation:** anyone. The factory calls it in the same transaction that deploys the wallet, so in practice no one else can call it first.

```rust
pub fn init(
    env: Env,
    initial_signer: BytesN<65>,
    rp_id: Bytes,
    origin: Bytes,
) -> Result<(), WalletError>
```

Stores the first signer at index 0 and sets the nonce to 0. It also stores the WebAuthn relying-party ID and origin, which `__check_auth` checks on every passkey signature. `initial_signer` is an uncompressed P-256 public key (`0x04 || x || y`).

**Errors:** `AlreadyInitialized` if the wallet already has a signer.

### `add_signer`

**Status:** Live on mainnet, but the mainnet signature is different · **Authorisation:** wallet owner

```rust
// main
pub fn add_signer(env: Env, new_public_key: BytesN<65>) -> Result<u32, WalletError>

// mainnet (ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2)
pub fn add_signer(env: Env, new_public_key: BytesN<65>) -> u32
```

Adds another passkey public key and returns the index it was given. Indices come from a counter that only goes up, so an index freed by `remove_signer` is never reused.

**Errors:** on `main`, `SignerAlreadyExists` if the key is already registered. The mainnet version returns a plain `u32` and has no such check, so adding a key twice gives it a second index.

### `remove_signer`

**Status:** Live on mainnet · **Authorisation:** wallet owner

```rust
pub fn remove_signer(env: Env, index: u32) -> Result<(), WalletError>
```

Removes the signer at `index`. It refuses to remove the last signer.

**Errors:** `CannotRemoveLastSigner`, `SignerNotFound`.

### `rotate_signer`

**Status:** Live on mainnet · **Authorisation:** wallet owner

```rust
pub fn rotate_signer(
    env: Env,
    old_public_key: BytesN<65>,
    new_public_key: BytesN<65>,
) -> Result<(), WalletError>
```

Replaces one signer key with another in a single step, for when a device is replaced. The new key takes the old key's index. The wallet address and its balances do not change.

**Errors:** `InvalidPublicKey` if the two keys are the same, `SignerAlreadyExists` if `new_public_key` is already registered, `SignerNotFound` if `old_public_key` is not a signer.

### `__check_auth`

**Status:** Live on mainnet, but spend limits and session keys behave differently there · **Authorisation:** called by the Soroban host, never directly

```rust
pub fn __check_auth(
    env: Env,
    signature_payload: BytesN<32>,
    signature: Val,
    _auth_contexts: Vec<Context>,
) -> Result<(), WalletError>
```

The host calls this whenever the wallet's authorisation is required. It accepts three kinds of `signature`, tried in this order:

1. **Allowance.** `signature` is an `Address`. That spender must authorise the call, and every context must be a token `transfer` from this wallet. The amount is taken from the spender's allowance for that token (see `approve`).
2. **Session key.** `signature` is a `Vec<Val>` of `[key_id: BytesN<32>, ed25519_sig: BytesN<64>, nonce: u64]`. The ed25519 signature must verify against the key's registered public key, the nonce must match, and every context must pass the key's ACL. On success the nonce goes up by one.
3. **Passkey (WebAuthn).** `signature` is a `Vec<Val>` of `[public_key: BytesN<65>, authenticator_data: Bytes, client_data_json: Bytes, signature: BytesN<64>, nonce: u64]`. The key must be a registered signer and the nonce must match. `clientDataJSON` must be a `webauthn.get` assertion whose challenge is `base64url(signature_payload)`. The authenticator must report user presence and user verification, the RP ID hash and origin must match the stored values, and the P-256 signature must verify. Spend limits are then enforced, and on success the nonce goes up by one.

How the two versions differ:

- **Spend limits.** On `main`, limits are per (key, token). A key with any limit is scoped: moving a token it has no budget for, or making a call whose token movement cannot be read, is refused. On mainnet, a key has one limit, and it is checked against the sum of argument index 2 of every context, whatever token that is.
- **Session keys.** On `main`, amounts and payees are read per selector, and calls with an unknown selector are refused. On mainnet, the amount is argument index 2 when there is one, and otherwise 0.

**Errors:** `InvalidSignatureFormat`, `SignerNotAuthorized`, `NonceMismatch`, `InvalidCeremonyType`, `InvalidChallenge`, `InvalidAuthData`, `UserVerificationRequired`, `RpIdMismatch`, `OriginMismatch`, `InsufficientAllowance`, `AllowanceExpired`, `NegativeAmount`, `SessionKeyExpired`, `SessionKeyAclViolation`, `SpendLimitExceeded`. Only on `main`: `SpendLimitTokenNotAllowed`, `SpendLimitUnsupportedCall`. A bad P-256 or ed25519 signature is a host trap.

**Status:** Live on mainnet · **Authorisation:** wallet owner

### `approve`

**Status:** Live on mainnet, but it behaves differently there · **Authorisation:** wallet owner

```rust
pub fn approve(
    env: Env,
    spender: Address,
    token: Address,
    amount: i128,
    expiry: Option<u64>,
)
```

Lets `spender` move up to `amount` of `token` out of the wallet, until `expiry` if one is given. The spender uses this allowance through branch 1 of `__check_auth`. Calling `approve` again replaces the allowance.

- On `main`, `amount = 0` deletes the allowance, and a negative amount panics.
- On mainnet, any `amount <= 0` panics (`"Amount must be greater than 0"`). A mainnet allowance cannot be revoked by approving zero. Replace it with a small amount, or let it expire.

**Errors:** panics on an invalid amount, as described above.

### `revoke_allowance`

**Status:** Source only (not deployed) · **Authorisation:** wallet owner

```rust
pub fn revoke_allowance(env: Env, spender: Address, token: Address)
```

Deletes the allowance for (`spender`, `token`). This is the same as `approve(spender, token, 0, None)` on `main`. Mainnet wallets do not have this function.

### `get_allowance`

```rust
pub fn get_allowance(env: Env, spender: Address, token: Address) -> Option<storage::Allowance>
```

Returns the remaining `amount` and the `expiry` of an allowance, or `None` if there is none.

### `set_guardian`

**Status:** Live on mainnet · **Authorisation:** wallet owner

```rust
pub fn set_guardian(env: Env, guardian: Address)
```

Sets or replaces the guardian, the address that may start a guardian recovery. Emits a `("guardian", "set")` event.

### `initiate_recovery`

**Status:** Live on mainnet, but its errors are different there · **Authorisation:** guardian

```rust
pub fn initiate_recovery(env: Env, new_public_key: BytesN<65>) -> Result<(), WalletError>
```

Starts a guardian recovery that will replace every signer with `new_public_key` after a 3-day timelock (`RECOVERY_DELAY_SECONDS = 259_200`).

**Errors:** `NoGuardianSet`. On `main`, the guardian recovery and the recovery-key recovery share one slot, so the call fails with `GuardianRecoveryPending` or `RecoveryKeyRequestPending` if either is pending. On mainnet the two are separate, and the call fails with `RecoveryAlreadyPending` only if a guardian recovery is already pending.

### `complete_recovery`

**Status:** Live on mainnet, but its errors are different there · **Authorisation:** anyone, once the timelock has passed

```rust
pub fn complete_recovery(env: Env) -> Result<(), WalletError>
```

Finishes a guardian recovery. Every signer is replaced by the recovered key at index 0. The guardian, the recovery key, allowances, spend limits and session keys are not touched.

**Errors:** `RecoveryNotPending`, `RecoveryTimelockActive`. Only on `main`: `RecoveryKeyRequestPending`, when the pending recovery belongs to the recovery key.

### `cancel_recovery`

**Status:** Live on mainnet, but it behaves differently there · **Authorisation:** wallet owner

```rust
pub fn cancel_recovery(env: Env) -> Result<(), WalletError>
```

Cancels a pending recovery. On `main` it cancels whichever kind is pending, so nothing is left counting down. On mainnet it cancels only a guardian recovery. Use `cancel_recovery_request` for a recovery-key request.

**Errors:** `RecoveryNotPending`.

### `get_pending_recovery`

**Status:** Source only (not deployed) · **Authorisation:** anyone (read-only)

```rust
pub fn get_pending_recovery(env: Env) -> Option<PendingRecoveryStatus>
```

Returns the pending recovery, if there is one: which system started it (`Guardian` or `RecoveryKey`), the key it will install, and when it unlocks. Mainnet wallets do not have this function.

### `register_session_key`

**Status:** Live on mainnet · **Authorisation:** wallet owner

```rust
pub fn register_session_key(
    env: Env,
    pubkey: BytesN<32>,
    key_id: BytesN<32>,
    target_contract: Address,
    selector: Symbol,
    amount_cap: i128,
    expiry: u64,
)
```

Registers an ed25519 session key under `key_id`. The key can authorise calls to `selector` on `target_contract`, up to a total of `amount_cap`, until `expiry`. The ACL is kept in temporary storage, with a TTL that runs to the expiry. On `main` this is the same as `register_session_key_scoped` with no payee list and no per-call maximum.

### `register_session_key_scoped`

**Status:** Source only (not deployed) · **Authorisation:** wallet owner

```rust
pub fn register_session_key_scoped(
    env: Env,
    pubkey: BytesN<32>,
    key_id: BytesN<32>,
    target_contract: Address,
    selector: Symbol,
    amount_cap: i128,
    expiry: u64,
    payees: Vec<Address>,
    per_call_max: Option<i128>,
)
```

Works like `register_session_key`, with two extra limits. If `payees` is not empty, any other recipient is refused, and so is a call with no recipient. If `per_call_max` is set, no single call may spend more than it. Mainnet wallets do not have this function.

### `revoke_session_key`

**Status:** Live on mainnet · **Authorisation:** wallet owner

```rust
pub fn revoke_session_key(env: Env, key_id: BytesN<32>)
```

Deletes the session key straight away.

### `set_key_spend_limit`

**Status:** Live on mainnet, but the mainnet signature is different · **Authorisation:** wallet owner

```rust
// main
pub fn set_key_spend_limit(env: Env, key_id: BytesN<65>, token: Address, cap: i128)

// mainnet (ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2)
pub fn set_key_spend_limit(env: Env, key_id: BytesN<65>, cap: i128)
```

Sets a rolling 24-hour spend cap for a passkey signer, and resets its window. `cap = 0` blocks spending.

- On `main`, the cap is in the base units of `token`. Each (key, token) pair has its own window, and a key with any limit may move only the tokens it has a budget for. A key that has a limit cannot manage limits.
- On mainnet, a key has one cap, and it is compared with the sum of argument index 2 across every context, whatever the token.

### `remove_key_spend_limit`

**Status:** Live on mainnet, but the mainnet signature is different · **Authorisation:** wallet owner

```rust
// main
pub fn remove_key_spend_limit(env: Env, key_id: BytesN<65>, token: Address)

// mainnet (ccebd01a9b71c9857e6cd1e05dbdf6d45ea38ba2)
pub fn remove_key_spend_limit(env: Env, key_id: BytesN<65>)
```

On `main`, removes the key's limit for one token. If that was its only limit, the key is no longer restricted. On mainnet, removes the key's single limit.

### `remove_all_key_spend_limits`

**Status:** Source only (not deployed) · **Authorisation:** wallet owner

```rust
pub fn remove_all_key_spend_limits(env: Env, key_id: BytesN<65>)
```

Removes every per-token limit for a key, so it is no longer restricted. Mainnet wallets do not have this function. On mainnet, `remove_key_spend_limit` does the same job, because there is only one limit per key.

### `request_recovery`

**Status:** Live on mainnet, but its errors are different there · **Authorisation:** recovery key

**Errors:** `NoRecoveryKeySet`. On `main`, `RecoveryKeyRequestPending` or `GuardianRecoveryPending` if either recovery is pending. On mainnet, `RecoveryAlreadyPending` only if a recovery-key request is already pending.

## Factory contract

The factory deploys each wallet at an address derived from the factory's address and `salt = SHA-256(public_key)`, and calls `init` on it in the same transaction. **On mainnet it has three entrypoints:** `__constructor`, `init` and `deploy`. Source on `main` adds a fourth, `set_wasm_hash`, which is not deployed. The mainnet factory therefore can never change the wallet code it deploys.

```rust
#[contracterror]
pub enum FactoryError {
    AlreadyInitialized = 1,
    NotInitialized     = 2,
    AlreadyDeployed    = 3,
    InvalidPublicKey   = 4,
}
```

### `__constructor`

**Status:** Live on mainnet · **Authorisation:** runs once, as part of the deploy transaction

```rust
pub fn __constructor(env: Env, admin: Address)
```

Stores the factory admin while the contract is being created, so no one can get in before it.

### `init`

**Status:** Live on mainnet · **Authorisation:** factory admin

```rust
pub fn init(env: Env, wasm_hash: BytesN<32>) -> Result<(), FactoryError>
```

Stores the hash of the wallet WASM that `deploy` will install. It can only run once.

**Errors:** `NotInitialized` if no admin is stored, `AlreadyInitialized` if a hash is already stored.

### `set_wasm_hash`

**Status:** Source only (not deployed) · **Authorisation:** factory admin

```rust
pub fn set_wasm_hash(env: Env, new_hash: BytesN<32>) -> Result<(), FactoryError>
```

Points future `deploy` calls at a new wallet WASM. It does not change any wallet that already exists, or any wallet address. The mainnet factory does not have this function, so the wallet code it deploys is fixed forever.

**Errors:** `NotInitialized` if no admin is stored or `init` has not run.

### `deploy`

**Status:** Live on mainnet · **Authorisation:** anyone

```rust
pub fn deploy(
    env: Env,
    public_key: BytesN<65>,
    rp_id: soroban_sdk::Bytes,
    origin: soroban_sdk::Bytes,
) -> Result<Address, FactoryError>
```

Deploys a wallet for `public_key`, calls `init(public_key, rp_id, origin)` on it, and returns its address. The same public key always gives the same address.

**Errors:** `NotInitialized` if no WASM hash is stored, `InvalidPublicKey` if the key is malformed, `AlreadyDeployed` if a wallet already exists for this key.

The `InvalidPublicKey` check is different in the two versions. On `main`, the key must start with `0x04` and be a point on the P-256 curve. On mainnet, only the `0x04` prefix is checked. The curve check there was compiled into test builds only, so a key that is off the curve gets a wallet, but no signature can ever verify against that key.

## Dependencies

Both contracts, on `main` and at the deployed commit, depend on:

```toml
[dependencies]
soroban-sdk = "22.0.0"
```

That is the only runtime dependency in the deployed commit. On `main`, the factory also depends on `p256 = { version = "0.13", default-features = false, features = ["ecdsa"] }` for its on-curve key check (see [`deploy`](#deploy)). The wallet has no other runtime dependency in either version. It verifies P-256 signatures with the host's `secp256r1_verify`.
